# 영창 시퀀스 Judge 계약 매트릭스

> 작성일: 2026-07-30  
> 브랜치: `codex/experiment-sequence-fixture-alignment`  
> 목적: 초기 R1 시퀀스 설계, 실제 런타임·validator, 현행 R2 Worker 프롬프트의 차이를 확인하고 실험용 Judge 재설계의 기준을 고정한다.  
> 범위: 감사·실험 기준. 프로덕션 계약 변경은 R2 리뷰와 별도 PR이 필요하다.
> 의도·안무 품질 기준: `SEQUENCE_JUDGE_INTENT_MODEL.md`

## 1. 기준 자료와 우선순위

| 우선순위 | 자료 | 용도 |
|---:|---|---|
| 1 | `src/spell/sequencePlan.ts`, `spellPlanValidate.ts`, `validate.ts` | 현재 실제로 실행·검증되는 하드 계약 |

## 2. Issue #203에서 채택된 판정 정책

### 2.1 역할

- 기존 R1 30종은 프롬프트 few-shot이 아니라 **공개 기능·회귀 코퍼스**다.
- 30종 결과만으로 일반화 성능을 판단하지 않고 별도 held-out을 사용한다.
- 정확한 fixture JSON 일치보다 권장 모드, 의미 anchor, 실제 게임 기전 보존을 평가한다.
- 전체 시퀀스 비율만 맞추는 방식은 불합격이다.

### 2.5 현행 기준군의 형식 게이트 결과

| 지표 | 현행 결과 | 판정 |
|---|---:|---|
| 시퀀스 권장 19종 | 17종 시퀀스 | 통과 |
| 단일 우선 11종 | 8종 단일 | 통과 |
| 단일 우선의 시퀀스 확장 | 3종 | 허용 상한 |
| 초기 병렬 사례 | 1/18만 병렬 유지 | 구조 품질 실패 |
| 초기 단계 수 | 4/30 일치 | 구조 품질 실패 |

현행 Worker는 #203의 단일/시퀀스 분포 기준을 통과하면서도 안무 품질이 낮다. 따라서 새 평가 계약은 기존 19/11 게이트를 유지하되 병렬성, 사건 순서, wait 박자, 피날레, 구조 다양성, 변수값 적합성을 별도 축으로 추가해야 한다.

### 2.6 수량 해석 우선순위

1. 안전 제한과 로컬 상한
2. 원소와 핵심 효과
3. 주문의 목적과 방향
4. 명시적 수량
5. 세부 연출

- 핵심 수량은 가능한 범위에서 기전에 반영한다.
- 규모·강조 수량은 다중 공격·밀도·범위로 압축할 수 있다.
- 비유와 고유명에 포함된 숫자는 기계적 수량으로 강제하지 않는다.
- 동일 signature의 동시 form은 런타임에서 중복 제거되므로 개수·밀도는 `size`·형태로 압축하고, 실제 원소·효과·형태가 다른 사건만 병렬 behavior로 분리한다.

| 역할 | 권장값 |
|---|---:|

| 전체 원소 수 | 제한 없음 | 추상 `3×2` 제한으로 사실상 축소 | 하드 behavior 상한 안에서 명시 원소 보존 | Worker 수정 |
| status | 6종 중 0~3 | 동일 | 의미 있는 상태만 | 일치 |
| summon behavior | summon이고 움직임 묘사 있을 때 | 동일 | 1~6번 기존 계약 유지 | 범위 밖 |
| wall shape | wall이고 형상 묘사 있을 때 | 동일 | 1~6번 기존 계약 유지 | 범위 밖 |

`effect`, `target`, `form`, 원소는 하나의 대표 effect를 먼저 정해 전체 plan에 복제하지 않고 각 form behavior마다 독립 판정한다.

## 10. `MoveBehavior`

| 항목 | 초기 설계문서 | 실제 런타임·validator | 현행 Worker | 실험 기준 | 상태 |
|---|---|---|---|---|---|
| 원소 | 필수 | 필수 | 필수 | 유지 | 일치 |
| destination | 8종 | 8종 화이트리스트 | 6종만 노출 | 런타임 8종 전부 노출 | **확정** |
| 누락 destination | 없음 | `cast-direction`, `random-enemy` 지원 | 두 값 누락 | 두 값도 다른 destination과 동일하게 사용 | **확정** |
| 기본 거리 | 180px | 미지정 시 런타임 기본 | 설명 없음 | 일반 이동은 생략해 로컬 기본값 사용 | **확정** |
| 최대 거리 | 420px | resolve에서 clamp | 1~420 | 유지 | 일치 |
| 각도 | 화면 위 0, 시계방향 | 동일 | 동일 | 유지 | 일치 |
| `custom-vector` | angle·distance 사용 | 숫자가 있으면 수용 | 둘 다 필수 지시 | 방향 명시 시 둘 다 출력 | 대체로 일치 |
| 순간이동 | 별도 type 없음, 0ms 이동 | 동일 | 별도 설명 없음 | duration/단계 시간으로 표현 | 보완 필요 |
| 같은 단계 move | 하나만 유지 | destination과 무관하게 중복 제거 | 설명 없음 | 한 단계에 move 최대 하나 생성 | 보완 필요 |

### distance 책임의 확정 실험 기준

- 일반적인 이동은 `distance`를 생략해 로컬 기본값을 사용한다.
- 짧게·멀리·맵을 가로질러처럼 거리감이 의미 anchor인 경우에만 제한 범위 안의 값을 출력한다.
- 정확한 픽셀값을 사용자 의미처럼 취급하지 않는다.

이 기준은 기존 스키마를 바꾸지 않고 “절대 픽셀을 LLM이 결정하지 않는다”는 원칙과 실제 distance 필드를 절충한다.

### move의 의미 책임

- `move`는 **플레이어 본체의 위치 변화**만 뜻한다. 플레이어가 별·새·빛 같은 이미지로 체현되어 비행·추격·순례하는 해석도 플레이어 이동으로 본다.
- 투사체·파도·유성·소환수 등 마법 형상의 이동은 해당 `form`과 `speed`로 표현하며 `move`를 추가하지 않는다.
- 입력에 플레이어의 돌진·도약·후퇴·점멸·보행이 없으면 시퀀스 형식을 만들기 위한 장식용 `move`를 생성하지 않는다.
- 이동과 공격이 같은 순간이면 같은 sequence에 병렬 배치하고, 이동 완료 후 공격이면 별도 sequence로 나눈다.

## 11. `WaitBehavior`

| 계약 | 기준 |
|---|---|
| 사용 목적 | 정적·준비·박자·지연 폭발 사이 간격 |
| 배치 | 반드시 wait-only sequence |
| 같은 단계 혼합 | 다른 behavior가 있으면 wait 제거 |
| 중복 | wait-only 단계에서 하나만 유지 |
| 시간 | 해당 sequence의 `durationWeight` 비율만큼 소비 |
| 필수 사용 예 | 명시적 박자, 두 타격 사이 간격, 잠듦→각성, 형성→지연 폭발 |
| 금지 | 단계를 늘리기 위한 무의미한 대기 |

현행 Worker는 wait을 타입으로만 정의하고 판단·예시를 제공하지 않아, 새 7번에는 최소 하나의 비중복 예시가 필요하다.

## 14. 현행 Worker의 주요 계약 이탈 요약

1. 융합된 이동과 공격도 별도 sequence로 강제해 병렬 계약과 충돌한다.
2. 추상 입력에만 `3 sequence × 2 behavior`를 적용해 런타임의 `10 × 5` 표현 범위를 축소한다.
3. `팔원소` 보존 요구와 최대 6 behavior 예산이 충돌한다.
4. `SpellPlan.power` 출력 예시가 `0`이라 전체 예산 계약과 충돌한다.
5. `durationWeight`, `powerWeight`, `tuning`의 의미와 적정값 유도가 없다.
6. wait-only 박자 계약을 설명하거나 보여주는 예시가 없다.
7. move destination 8종 중 2종이 프롬프트에서 누락됐다.
8. 추상/정적 명사 예외가 사건 구조보다 우선해 명시적 반복·변화를 축약할 수 있다.
9. “수량 1”을 물체 수가 아니라 사건 수로 취급해 무조건 단일화한다.
10. 30종은 회귀 코퍼스로 채택됐으나 현행 튜닝의 구조 품질 평가에는 단계·병렬성·변수 계약이 포함되지 않았다.
