## 기록 규칙

- 모든 작업 항목과 페이즈 제목에 `[R1]` 태그를 붙인다.
- 새로운 R1 작업은 기존 내용을 덮어쓰지 않고 페이즈 또는 작업 묶음 단위로 아래에 추가한다.
- R1에 계획된 역할과 R1이 실제 수행한 작업을 구분해 기록한다.
- 작업 기간, 담당자, 브랜치, 커밋, 주요 산출물과 검증 결과를 함께 남긴다.
- 임시 구현이나 팀 합의가 필요한 부분은 확정 사항과 구분한다.
- 완료되지 않은 항목은 체크하지 않고 다음 작업으로 이월한다.
- 다른 역할의 작업 실적은 이 문서에 대신 작성하지 않고, R1 코드와 직접 맞닿는 인터페이스·협업 사항만 기록한다.

### 주요 구현 결과

#### 소스 구조와 역할 경계

- R1 전용 전투 로직은 `src/combat-core/` 아래의 `combat`, `enemies`, `player`, `waves`로 구성한다.
- 여러 역할이 함께 사용하는 `src/render/`, `src/scenes/`와 공용 진입점 `src/main.ts`는 최상위 위치를 유지한다.
- R2 계약 영역인 `src/spell/`도 최상위 위치를 유지한다.
- `ProtoScene`과 주문 렌더러는 `SpellSpec`을 참조하되 R2 스키마 구조를 변경하지 않는다.

#### 플레이어와 카메라

- WASD로 이동하며 대각선 입력 시 속도를 정규화한다.
- 카메라는 플레이어를 부드럽게 추적하고 HUD는 화면에 고정된다.
- 영창 입력 중에는 플레이어 이동을 차단하고 게임 진행 시간을 10%로 낮춘다.
- 플레이어 상태는 HP 100, 마나 100을 기준으로 관리하며 마나 비용과 글로벌 쿨다운을 검사한다.

#### 적과 피해 처리

- 추격자는 플레이어를 직선으로 추적하고 개체별 쿨다운으로 접촉 피해를 준다.
- 사수는 선호 거리를 유지하면서 3발 확산 탄막을 발사하고 접촉 피해도 준다.
- 대형 분열체는 처치 시 소형 분열체 2기로 나뉘며, 소형까지 모두 처치해야 웨이브가 끝난다.
- 기본 공격은 가장 가까운 적을 추적하고 적중 즉시 사라지며 관통하지 않는다.
- 주문 피해의 1차 공식은 `round(power)`이며, 폼별 최종 밸런스는 후속 작업으로 남겼다.

#### 웨이브와 주문 폼

- 웨이브 1: 추격자 3기
- 웨이브 2: 추격자 2기 + 사수 2기
- 웨이브 3: 추격자 2기 + 사수 2기 + 대형 분열체 1기
- 마지막 활성 적을 처치하면 웨이브 완료 또는 `ROOM CLEAR` 상태로 전환한다.
- `beam`은 목표 방향의 직선 범위를 관통하며 범위 안의 적을 각각 한 번 타격한다.
- `wave`는 넓은 파면이 전진하며 닿은 적을 각각 한 번 타격한다.
- `size`, `speed`, 주·보조 원소 팔레트를 두 폼의 크기·속도·색상에 반영한다.

### 임시 구현 및 후속 협의 항목

다음 내용은 GDD에 구체적인 값이나 동작이 없어 프로토타입 검증을 위해 임시로 정했다.

- 스크롤 카메라와 화면 2배 크기의 직사각형 월드
- 마나 회복량, 이동·공격 속도와 적별 피해 수치
- 기본 공격 사거리 `400px` 및 피해 `10`
- 1분 이내 3웨이브 검증을 위한 적 HP: 추격자 `30`, 사수 `20`, 대형 분열체 `40`, 소형 분열체 `10`
- 웨이브별 적 조합과 웨이브 사이 2초 대기
- `beam` 사거리·폭·관통 방식과 `wave` 사거리·폭·이동 속도
- 주문 상태이상과 넉백은 이번 범위에서 제외
- 주문명 공통 최대 길이 `30자`와 긴 이름 자동 줄바꿈

해당 값은 플레이테스트와 팀 합의 후 확정하거나 교체해야 한다.

### 구현 내용과 결정

- **적 단위 히트스톱**으로 구현해 게임 전체와 플레이어 조작은 멈추지 않는다. 일반 타격은 0.11초, 빠르게 반복되는 `zone`·`orbit`은 0.02초를 적용하고 `rain`·`wall`은 일반 타격으로 분류했다. 보스와 실드 차단 피해에는 적용하지 않으며, 중복 타격은 시간을 더하지 않고 더 긴 반응만 유지한다.
- **카메라 셰이크 강약 계층**을 weak/medium/strong으로 통합했다. 더 강한 셰이크는 진행 중인 약한 셰이크를 교체하고 반복 약한 셰이크는 짧은 쿨다운으로 제한한다. 직접 영창을 자동 각인·정령 공격보다 강조하며, 특히 `beam`과 `nova`를 강하게 설정하고 보스 돌진 종료 셰이크는 낮췄다.
- **방향성 스쿼시**를 적 공통 피격 경로로 이동해 추적형·사수형뿐 아니라 분열형·실드셋·엘리트에도 같은 규칙이 적용되도록 했다. 기존 개별 피격 반응은 섬광만 담당해 scale 트윈 중복을 제거하고, 원래 스케일을 보존한다. 보스는 위치 넉백 없이 약한 스쿼시만 사용한다.
- `status: knockback`은 스쿼시와 병렬로 실제 적 위치를 밀어낸다. 일반 공격 36px, `zone` 12px, `orbit` 18px로 지속 공격의 누적 밀림을 낮추고 월드 경계 밖으로 나가지 않도록 제한했다. damage/control/summon 경로와 정령 투사체에도 상태값이 보존된다.
- 타격 반응 수치와 분류는 `hitStopConfig.ts`, `cameraShakeConfig.ts`, `knockbackConfig.ts`에 분리해 후속 밸런싱에서 전투 로직을 다시 건드리지 않고 조정할 수 있게 했다.

- 초기에는 Issue #77의 `시야 축소 → 광역·설치형 주문의 가치 상승`을 주문별 국소 광원으로 구현했다. 플레이테스트 결과 광역기 자체로 적이 정리되거나 마나가 소진돼 밝혀진 시야의 후속 활용이 어려웠고, 폼별 광원 추적은 규칙 전달도 불명확해 폐기했다.
- 최종 프로토타입은 빛·불꽃 속성의 **직접 영창**이 시야 반경을 2배로 넓힌다. 정령·각인·주문서 자동 발동은 제외해 플레이어가 의식적으로 원소를 섞어야 한다.

- 조명 시간은 현실 시간이 아니라 전투 시간으로 감소한다. 영창 입력 슬로모션 중 시간이 거의 소진되지 않아 밝혀진 시야를 다음 주문에 활용할 수 있다. 연속 발동은 남은 시간을 초기화한다.
- 암전 렌더러는 플레이어 주변 기본/2배 반경의 5겹 그라데이션 역마스크 두 세트와 교차 페이드 값만 소유한다. 폐기한 임시 광원 배열·폼별 이동 콜백·광륜 렌더링은 모두 제거했으며 별도 암전 해제 텍스트도 띄우지 않는다. 방 진입 안내도 `빛/불꽃 기술을 쓰면 밝아집니다`로 단순화했다.
- 보스 탄막·돌진·장판 예고처럼 회피에 필수인 정보는 암전 위에 남긴다. HUD·영창 UI도 월드 암전의 영향을 받지 않는다.
- 저주를 의도에 따라 `movement`·`element`·`casting` 카테고리로 먼저 나눈다. 후보가 있는 카테고리 중 최대 2개를 결정적 랜덤으로 고른 뒤, 각 카테고리 내부에서는 직전 런 행동 가중치가 가장 높은 저주 1종을 선택해 저주방에 교대로 배분한다. 현재는 이동 카테고리의 침묵과 원소 카테고리의 암전만 있어 둘 다 자동으로 선택된다. `casting`은 주문 반사 같은 후속 저주를 위한 빈 카테고리다.

## [R1] Phase 5 — 파티션 기반 맵 설계·MapGraph 기반 구현

### 작업 개요

| 항목 | 내용 |
|---|---|
| 작업 기간 | 2026-07-28 |
| 담당 영역 | R1 런 맵 구조 설계·순수 그래프 모델·검증 도구 |
| 담당자 | 이도원 (`dowon03`) |
| 브랜치 | `docs/partition-map-design`, `feat/map-graph-foundation` |
| 목표 | Issue #214의 분기형 스테이지를 Phaser 런타임과 분리해 설계·시각 검증하고, 후속 포탈·미니맵·방 전환이 소비할 최소 MapGraph 계약을 마련 |
| 구현 상태 | 설계 문서·시뮬레이터·순수 모듈·회귀 완료, 런타임 통합 대기 |

### R1 수행 작업과 협업 경계

- **R1 수행 작업**: `a>b(n)` 파티션 문법, 스테이지 방 예산·루트 위험/보상·방 종류 우선순위, 시드 기반 HTML 시뮬레이터, `MapGraph` 계약/프리셋/검증을 구현했다.
- **R2/R3 작업 경계**: 실제 방 전환·포탈·미니맵 소비, 보상/제단의 최종 위험도·보상 기대치 튜닝, 생성된 그래프의 런타임 선택과 저장은 후속 통합 범위다.

### 주요 결정

- 파티션은 시작 분기 수 `a`, 종료 분기 수 `b`, 평균 경로 길이 `n`을 갖는 `a>b(n)`으로 표현한다. 분기는 최대 3개로 제한하고, 선형·분기·합류를 조합해 DAG를 구성한다.
- 루트 선택의 의미를 유지하기 위해 위험도가 높은 경로에는 상대적으로 높은 보상을 배치하되, 전체 노드 기준 전투/비전투 비율과 방 종류 다양성을 함께 고려한다.
- 생성 제약은 안전성/도달성, 스테이지당 보상방 최소 1개, 루트 위험·보상 정합성, 방 종류 다양성, 전투·비전투 및 전투방 유형 비율 순서로 검증한다.
- HTML 시뮬레이터로 시드별 구조·방 구성·예상 런타임을 확인하고, 코드 감사기로 다수 시드의 제약 위반 여부를 점검했다.
- Phaser 의존성이 없는 `MapGraph` 모듈과 계약·프리셋·회귀 스크립트를 먼저 구현해, 후속 런타임 통합에서 그래프 생성 규칙을 재작성하지 않도록 했다.

### Worker 7번 실험 프롬프트 재작성

- 런타임 계약에 맞춰 move destination 8종을 모두 노출하고, 일반 distance는 로컬 기본값에 맡기며 거리 의미가 핵심일 때만 LLM이 제한값을 내도록 확정했다.
- `move`를 플레이어 본체 이동으로 한정했다. 투사체·파도·유성·소환수 이동이나 시퀀스 형식을 만들기 위한 장식용 이동에는 사용하지 않는다.

- 이동+공격의 관계에 따라 같은 단계 병렬 또는 순차 단계를 구분하고, wait-only, 전체 plan Power, durationWeight, powerWeight, tuning의 상대값 계약과 출력 전 자체검사를 추가했다.
- 완전히 같은 병렬 form은 런타임에서 중복 제거되므로 동일 공격 수량은 크기·밀도로 압축하고, 실제 원소·효과·형태가 다른 사건만 병렬 behavior로 나누도록 명시했다.
- 새 Judge prompt는 기존 6,914자에서 6,701자로 213자(3.1%) 감소했다.
- `node --check proxy/worker.js`, `npm run test:planvalidate`(15군), `npm run build`를 통과했다.
- 이 초안 작성 시점에는 미배포 상태였으며, 이후 아래 후보 1~5를 프로덕션과 분리된 실험 Worker에서만 측정했다. prompt version 변경과 실적용은 실험 결과 및 R2 검토 이후다.

- Worker 응답 본문과 판정 의미는 바꾸지 않고 `Server-Timing`, Gemini 판정 횟수, 입력·출력·캐시 토큰, 재판정 사유를 진단 헤더로 추가했다. 안정성 수집기도 해당 값을 저장한다.
- 후보 59 계측에서 고정 프롬프트는 호출당 약 11,230토큰, 명시적 캐시 적중은 0이었다. `팔원소 대합창` 10회는 1회 판정 7건, 2회 2건, 3회 1건이었고 최대 6.948초 사례는 3회 판정이었다. 확인된 재판정 사유는 JSON 문법 복구와 unsupported form이었다.
- 후보 60은 프롬프트 의미를 유지한 채 Gemini structured output으로 JSON·enum을 강제하려 했으나 진단 버전 3에서 3/3 upstream 400 `INVALID_ARGUMENT`가 재현되어 기각했다.
- 후보 61은 동일 프롬프트를 `systemInstruction`으로 분리해 암묵 캐시를 유도했으나 캐시 적중이 계속 0이었고 `팔원소 대합창` 10회 중 2회가 12초 측정 상한을 넘겨 기각했다.
- 후보 62는 JSON 문법·unsupported form만 기존 응답을 보존하는 소형 재판정으로 복구하려 했으나 반복 10/10이 12초 측정 상한을 넘겼다. 외부 API 지연과 후보 자체 영향을 성공 헤더로 분리할 수 없었지만 기준선보다 명백히 불안정하므로 기각했다.
- 기각 후보의 요청 형식과 재판정 변경은 모두 제거했다. 실험 Worker는 후보 58의 원래 프롬프트·전체 계약 재판정과 진단 헤더만 유지한 버전 `37e230f4-651e-4909-80cb-25eab2c212d8`로 복구했다.
- 이번 단계에서는 품질을 보존한다는 조건으로 채택할 수 있는 Worker 응답시간 최적화가 확인되지 않았다. 공통 6초로 fallback 위험을 먼저 낮추고, 프롬프트 축약이나 명시적 context cache는 별도 품질 실험 없이는 적용하지 않는다.

### 플레이테스트 직전 원격 장애와 롤백

- 최종 수동 테스트를 시작할 때 모든 영창이 fallback되는 현상이 발생했다. 배포 Worker에 `파이어볼`을 직접 요청해도 15초 안에 HTTP 응답이 오지 않아 특정 영창 해석이나 클라이언트 캐시 문제를 배제했다.
- 실험 계측 배포의 영향을 제거하기 위해 Cloudflare Worker를 기존에 42/42 정상 응답을 검증한 후보 58 버전 `98aace9c-30d1-46e3-b961-64f9c51abfb2`로 100% 롤백했다.
- 롤백 후 동일 `파이어볼` 직접 요청도 다시 15초 timeout이었다. 따라서 현재 장애는 후보 59~62 코드가 아니라 Gemini upstream 과부하 또는 API 키·프로젝트 쿼터 경로로 분류한다.
- 원격 판정이 회복되거나 새 프로젝트의 API 키를 적용하기 전에는 수동 품질 테스트 결과를 유효하게 판정하지 않는다. 클라이언트의 fallback은 이 외부 장애에서 게임 정지를 막는 정상 안전 동작이다.

### 새 API 키 적용 후 원인 특정

- 새 키·Worker 재배포 뒤 실제 게임 주소 `incant-judge-proxy.diawodbsdot.workers.dev`에 `파이어볼`을 직접 요청했다. Worker는 약 0.7~1.0초에 HTTP 502를 반환해 현재 fallback이 6초 클라이언트 timeout 때문이 아님을 확인했다.
- Worker가 전달한 Gemini 상류 응답은 HTTP 400 `FAILED_PRECONDITION`이며 상세 메시지는 `User location is not supported for the API use.`였다.
- 따라서 새 키의 유효성이나 후보 58 프롬프트 처리시간보다 Cloudflare Worker에서 Gemini API로 나가는 호출의 지역 판정이 현재 차단 원인이다. 지역 경로를 교정하기 전 플레이 품질 측정을 재개하지 않는다.

### placement 제거 대조 실험

- 로컬 `.env.local`의 `VITE_JUDGE_PROXY_URL`은 게임 기본 주소가 아니라 실험 주소 `incant-judge-proxy.incant-judge-proxy.workers.dev`를 가리킨다. 따라서 현재 로컬 플레이 fallback은 앞서 400을 반환한 기본 주소와 별도로 판정해야 한다.
- 실험 Worker에서 `[placement] region = "gcp:asia-northeast1"`을 제거해 버전 `35700f0c-5ecb-4440-91e2-ce56ba314cdb`을 배포했으나 `파이어볼` 요청은 15초 안에 응답하지 않았다. placement 제거로 지역 오류나 장기 대기가 해결되지 않았다.
- 실험 후 도쿄 placement를 복원하고 버전 `c8e63bc0-0bcf-40a4-a779-1f3f6d7b63b5`를 배포했다. 현재 로컬 fallback의 직접 원인은 실험 Worker 내부 Gemini fetch가 클라이언트 6초 제한보다 오래 대기하는 것이며, 후보 58의 JSON 처리 단계까지 도달했는지는 응답이 없어 확인할 수 없다.
- 복구 버전에 Wrangler tail을 연결하고 70초 제한으로 다시 호출한 결과 `파이어볼`은 총 35.793초 뒤 HTTP 200으로 정상 완료됐다. 진단 헤더의 Gemini 시간은 35.464초, 판정 횟수 1회, 재판정 없음, 입력 11,227토큰, 출력 106토큰, 캐시 적중 0이었다.
- 따라서 Worker 진입·JSON 파싱·후처리 문제가 아니라 Gemini 첫 생성 호출 하나가 비정상적으로 느린 상태임을 확정했다. 6초 timeout 확대만으로는 이 상태를 실용적으로 흡수할 수 없다.

### 최종 수동 플레이 품질 확인 (2026-07-31)

- 사용자가 후보 58을 실제 게임에서 다시 플레이테스트한 결과, 판정 결과와 시각적 영창 경험에는 특별한 문제를 확인하지 못했다. fallback까지 이어지는 경우는 드물었지만 정상 응답도 약 4~5초 기다리면 영창 흐름상 길게 체감됐다.
- 이에 따라 후보 58의 영창 품질 검증은 통과로 정리한다. 남은 응답 지연은 단순 fallback 안정성뿐 아니라 정상 성공 응답의 UX 문제로도 다루며, 이후 최적화는 현재 품질을 기준선으로 보존하면서 체감 대기시간을 줄여야 한다.
